## Top findings, worst first

1. **Script injection in ComptoxR `record-cassettes.yml`, line 62.** It runs `args <- c("--record-live", "--workers", "${{ inputs.workers }}", "--batch-size", "${{ inputs.batch_size }}")`, interpolating free-text dispatch inputs into R source in a job that holds the live API key. Anyone with dispatch rights can run arbitrary code. Fix: pass the inputs through `env:` and validate them as integers.
2. **ComptoxR `pipeline-tests.yml` can re-record cassettes from production in CI.** The `rerecord_cassettes` input deletes fixtures and runs with `ctx_api_key`, contradicting the README policy that record-cassettes is the only live path. The same file uses `dacbd/create-issue-action@main` (unpinned branch ref) with no permissions block, and that issue step is dead code: it never fires on the `pull_request` trigger.
3. **QRMA_VFAR release is broken.** `release.yaml` line 98 runs `source("dev/normalize_news.R")`, but `QRMA_VFAR/dev` contains only `validation/`. Every release fails after the local commit and tag. Commit the script, or fall back to plain autonewsmd as boosterpak does.
4. **Secrets reach jobs that do not need them.** `ctx_api_key` is exposed to routine test-coverage, coverage-check, test-quick, and pipeline-tests jobs in ComptoxR, against its own CRAN-safe policy. epa-sswqs exposes its PAT and `ctx_api_key` at job level to every step, including the apt step and third-party actions.
5. **ComptoxR `rebase-WIP-branches.yml` is broken and dangerous.** The condition has a typo, `github.event. review.state` (line 11). It force-pushes other branches automatically using hyphen prefixes that do not match the Conventional Branch names in use, and it swallows errors. Delete it.
6. **Releases can leave orphan tags and bypass branch protection.** boosterpak, chorus, concert, and QRMA_VFAR push main and the tag non-atomically, then create the release. A partial failure leaves a tag that the existing-tag guard then refuses to rerun past. specmill pushes with `GITHUB_TOKEN` only, which fails on a protected main. The `RELEASE_PAT` scope is undocumented.
7. **Several projects have no automatic CI.** specmill `check.yml` is `workflow_dispatch` only. serapeum has `renv.lock`, 30+ testthat files, and Playwright, but its only CI is gitleaks. maestro never runs biome, `tsc --noEmit`, clippy, or tests, and its rust-cache path (`src-tauri`) is wrong for the root Cargo workspace, so the cache does almost nothing.
8. **Check gaps in ComptoxR.** Seven workflows share a `paths-ignore` block that excludes `DESCRIPTION`, `NAMESPACE`, and `.github/**`, so dependency, export, and workflow changes merge unchecked. Separately, R CMD check matrices everywhere are release-only, even where DESCRIPTION declares R >= 4.1.0.
9. **Action pinning drifts with no update path.** checkout runs v4, v5, v6, and v7 across repos (and within a single repo). gitleaks-action is v2.3.9 in some repos and v3.0.0 in others. r-lib/actions is on v2.12.1 against a current v2.14.0. Floating tags and SHA pins are mixed in the same repo. `dependabot.yml` exists only in boosterpak, chorus, concert, and ComptoxR.
10. **Least-privilege and runaway controls are missing across the board.** pkgdown jobs hold `contents: write` on PR runs. coverage-check and pipeline-tests call write APIs without declaring permissions. Almost no job sets `timeout-minutes`, so jobs default to 6 hours. Most CI has no concurrency cancellation, including ComptoxR's 6-leg test-coverage, which runs tests up to 3 times per leg. commit-lint's scope regex is wrong in 4 of 5 copies (`[a-z0-9_-]+` versus the autonewsmd rule `[A-Za-z0-9_]+`), and it only covers PRs to main, not integration.

### ComptoxR

#### `.github/workflows/r-cmd-check.yaml` (quality: good)

- Purpose: Standard R CMD check via r-lib/actions/check-r-package on ubuntu, windows, and macos using R release
- Triggers: push to main, pull_request to main (both with paths-ignore), workflow_dispatch
- Template candidate: yes

Issues:

- paths-ignore skips DESCRIPTION and NAMESPACE, so a dependency or export change (for example, adding an Imports entry) merges without R CMD check. '.github/**' is also ignored, so edits to this workflow are never exercised on their PR.
- The R matrix only covers release. There is no oldrel-1 or devel leg (test-coverage.yml runs devel instead, which is inconsistent).
- No timeout-minutes.
- The bot skip `if: github.actor != 'github-actions[bot]'` means the automated schema PR (when opened with GITHUB_TOKEN) never gets checked.
- Good: actions pinned by SHA, permissions contents: read, concurrency per ref with cancel-in-progress, fail-fast: false, Windows TESTTHAT_PARALLEL workaround.

Template note: Only copy in this group. It is the best template candidate: SHA-pinned, has permissions and concurrency, and is close to the r-lib upstream example. Drop the DESCRIPTION/NAMESPACE paths-ignore before promoting it to a template.

#### `.github/workflows/test-coverage.yml` (quality: ok)

- Purpose: Cross-platform test run (3 OS x release/devel) plus covr coverage and Codecov OIDC upload on ubuntu-release
- Triggers: workflow_dispatch; push to main, dev, dev-*; pull_request to main, dev (paths-ignore on both)
- Template candidate: yes

Issues:

- Tests run up to three times per job: check-r-package runs tests, then devtools::test(), then covr::package_coverage() on ubuntu-release. That is costly across 6 matrix legs.
- It largely duplicates r-cmd-check.yaml (same OS set plus devel) and pipeline-tests/coverage-check (coverage).
- Actions use floating tags (actions/checkout@v7, r-lib/actions@v2, codecov/codecov-action@v7, posit-dev/setup-air@v1). The SHA-pinned files in this repo use a different pinning style.
- No concurrency group, so superseded PR pushes keep running 6 jobs. No timeout-minutes.
- id-token: write is granted at workflow level to all 6 legs, but only the ubuntu-release Codecov step needs it.
- ctx_api_key secret is exposed to the full test and check run on push. The README says routine CI must pass without it, so exposing it widens the blast radius for no reason.
- Hardcoded macOS brew deps (gettext libgit2 llhttp) and a pak-version workaround for macOS devel are brittle and project-specific.
- Installs air plus the pinned apipak toolkit on every leg, including Windows and macOS devel.
- paths-ignore excludes DESCRIPTION/NAMESPACE (same risk as r-cmd-check).
- Push branch filter dev-* conflicts with the Conventional Branch style (feat/..., fix/...) used elsewhere.

Template note: Only copy. As a template, split it into a pure check matrix (reuse r-cmd-check) and a single ubuntu coverage job modeled on r-lib's test-coverage.yaml.

#### `.github/workflows/build.yml` (quality: ok)

- Purpose: Cross-platform Tauri desktop build (macOS universal, Windows, Linux). Builds the maestro-mcp-server sidecar with cargo, runs tauri-action to bundle, and uploads dmg/msi/nsis/deb/AppImage artifacts.
- Triggers: push to main, pull_request to main, workflow_dispatch
- Template candidate: no

Issues:

- No top-level permissions: block. It passes GITHUB_TOKEN to tauri-apps/tauri-action but only needs contents: read, because no tagName/release is configured.
- No concurrency group. Repeated pushes or PR updates start duplicate 3-OS builds, and macOS minutes are expensive. Add a group on workflow+ref with cancel-in-progress for PRs.
- No timeout-minutes on the job. A hung macOS or Windows Tauri build can run for up to 6h.
- Bug: swatinem/rust-cache@v2 sets workspaces: src-tauri, but Cargo.toml at the repo root is a workspace (members src-tauri, maestro-mcp-server), so the target dir is ./target. The cache points at a nonexistent src-tauri/target and does almost nothing. Use workspaces: '. -> target' or drop the input.
- Non-reproducible install: 'rm -f package-lock.json && npm install' throws away the committed lockfile on every run. Use npm ci with the lockfile and setup-node cache: npm.
- No npm caching: setup-node has no cache: npm.
- node-version: 20 is hardcoded, and Node 20 has been EOL since April 2026. Move to 22/24 LTS or read it from .nvmrc/package.json engines.
- No lint, typecheck or test gate. biome.json exists but Biome never runs. tsc only runs indirectly through tauri beforeBuildCommand (npm run build), so a type error surfaces as a 3x full native build failure rather than a fast check. There is no cargo test, cargo clippy or cargo fmt --check.
- Brittle shell: the per-OS branching in 'Build MCP server' repeats the matrix logic inside bash with if/elif on matrix.platform. It would be cleaner as matrix fields (e.g. mcp_targets, bin_ext) or split steps with if:.
- Three near-identical upload-artifact steps gated by platform. A single step with matrix-provided artifact name and path globs would replace them.
- The matrix mixes floating runners (macos-latest, windows-latest) with pinned ubuntu-22.04. Runner-image changes on the -latest labels can break builds silently. Pick one policy.
- tauri-apps/tauri-action@v0 is a floating major. None of the actions are SHA-pinned (checkout@v4, setup-node@v4, upload-artifact@v4, dtolnay/rust-toolchain@stable, swatinem/rust-cache@v2). checkout@v4 is one major behind (v5 is used elsewhere in this group).
- No paths filter or paths-ignore, so docs/README-only commits trigger the full 3-OS native build.
- No macOS signing/notarization secrets. That is fine for a CI artifact, but the bundles are unsigned, which is worth documenting.
- fail-fast: false is set explicitly. That is appropriate for a platform matrix.

Template note: Only copy in the group. It is project-specific (Tauri + sidecar). The reusable parts are generic: the permissions/concurrency/timeout header, a Node setup with lockfile cache, and a Rust toolchain + rust-cache composite.

### serapeum

#### `.github/workflows/gitleaks.yml` (quality: good)

- Purpose: Secret scanning with gitleaks over full git history.
- Triggers: push and pull_request on [main, integration], workflow_dispatch, weekly cron '31 9 * * 1'
- Template candidate: yes

Issues:

- No concurrency group. It is cheap, but it is the only baseline item missing from the header.
- No timeout-minutes. The full-history scan (fetch-depth: 0) should be capped at around 10 minutes.
- No repo-local .gitleaks.toml / allowlist. serapeum commits config.yml, .Renviron, .mcp.json and test fixtures, which are likely false-positive or true-positive sources, and the scan runs on default rules only.
- gitleaks-action v2 needs GITLEAKS_LICENSE for organization-owned repos. This is fine for a personal account but will break if the repo moves to an org.
- The 'if: github.actor != github-actions[bot]' guard is the right shape but is undocumented. It is identical in both copies.
- The branch list [main, integration] is hardcoded. Only this line and the cron minute differ from the site copy, so it is a clean candidate for workflow_call with default-branch detection (or no branch filter at all).
- Pinning is good: actions/checkout and gitleaks-action are SHA-pinned with comments. Dependabot is needed to keep those SHAs fresh, and there is no .github/dependabot.yml.
- Missing from this repo entirely (not a flaw in this file): serapeum has renv.lock, tests/testthat (30+ test files) and playwright, but there is no R CI workflow (testthat / lint / air format check / Shiny smoke). Gitleaks is the only CI.

Template note: Byte-for-byte identical to seanthimons.github.io/gitleaks.yml except the branch list (main vs master) and the cron minute (31 vs 13, a deliberate stagger). Neither copy is better. Promote this one to a single reusable workflow_call in a shared repo.

### seanthimons.github.io

#### `.github/workflows/gitleaks.yml` (quality: good)

- Purpose: Secret scanning with gitleaks over full git history.
- Triggers: push and pull_request on [master, integration], workflow_dispatch, weekly cron '13 9 * * 1'
- Template candidate: yes

Issues:

- No concurrency group or timeout-minutes (same as the serapeum copy).
- No .gitleaks.toml. The site commits rendered docs/ HTML and _freeze/ JSON, which can hold embedded tokens or long base64 blobs that raise false positives. Consider a path allowlist for docs/ and _freeze/, or explicitly scanning them.
- The 'integration' branch in the filter may not exist in this repo. It looks copy-pasted from serapeum, where it is meaningful.
- Branch list is hardcoded (master).

Template note: Functionally identical to the serapeum copy. Either can be the source. Replace both with a caller stub for a reusable workflow.

#### `.github/workflows/publish.yml` (quality: ok)

- Purpose: Render the Quarto site with the frozen computations (freeze: true, so no R on CI) and deploy docs/ to GitHub Pages through the official Pages artifact/deploy actions.
- Triggers: push to master, workflow_dispatch
- Template candidate: yes

Issues:

- No PR build check. Broken renders are only found after merge to master. Add a pull_request trigger that runs build only, with deploy gated on 'if: github.event_name != pull_request'.
- Permissions are set workflow-wide (pages: write, id-token: write). Better to scope them per job: build gets contents: read, deploy gets pages/id-token write.
- concurrency group 'pages' with cancel-in-progress: false is the correct GitHub-recommended pattern.
- No timeout-minutes on either job.
- Quarto version is unpinned. quarto-dev/quarto-actions/setup@v2 without 'version:' takes the latest release, so renders can change or break when Quarto releases. Pin the version, ideally as an input.
- actions/checkout@v4 is one major behind the v5 SHA pin used in gitleaks.yml in the same repo. Actions are tag-pinned here but SHA-pinned in gitleaks, which is inconsistent within one repo.
- Redundancy/confusion: output-dir is docs and docs/ appears to be committed (it is not gitignored), yet CI re-renders into docs and deploys it. Either Pages is set to 'GitHub Actions' (then the committed docs/ is dead weight and a diff-noise source) or to branch/docs (then this workflow is redundant). Pick one.
- The freeze: true reliance is not guarded. If a post is added without its _freeze output, quarto render will try to execute R and fail with an unclear error because R is not installed. A step that fails fast on missing freeze, or installing R conditionally, would make this robust.
- No paths-ignore, so edits to .planning/, tasks/, scripts/ or tests/ trigger a deploy.
- The comment 'Quarto is cached automatically by this action' is questionable. The setup action downloads the release and does not persist a cache across runs.

Template note: Only copy in the group. It is a good base for a generic 'quarto-pages' reusable workflow once quarto version, output dir and branch are made inputs and a PR build-only path is added.

## Cross-repo drift

### ComptoxR (21 workflows, plus .github/dependabot.yml and .github/workflows/README.md)

- This group has only one repo, so all drift below is within ComptoxR.
- Action pinning is split. build-package, commit-lint, gitleaks, publish-*, release, and r-cmd-check pin by full SHA with version comments. api-compatibility-probe, coverage-check, cran-readiness, db-*, pipeline-tests, pkgdown, rebase-WIP, record-cassettes, schema-check, test-coverage, and test-quick use floating tags. api-compatibility-probe is still on actions/checkout@v4 and upload-artifact@v4 while the rest use v7. pipeline-tests uses dacbd/create-issue-action@main (branch ref).
- Permissions: 9 files have none (coverage-check, cran-readiness, pipeline-tests, test-quick, rebase-WIP at job level only, schema-check at job level, record-cassettes at job level, db-* at job level). coverage-check and pipeline-tests call write APIs without declaring them.
- Concurrency is present only in r-cmd-check, the db-* files, publish-*, and release. It is missing from test-coverage, coverage-check, pipeline-tests, test-quick, cran-readiness, schema-check, pkgdown, and gitleaks.
- timeout-minutes is present only in cran-readiness (30), schema-check (15), record-cassettes (120), and db-* (180/240/180).
- Token naming varies: GITHUB_PAT is set from `github.token` in some files and `secrets.GITHUB_TOKEN` in others. The CTX key is exposed as env `ctx_api_key` in test workflows but `CTX_API_KEY` in api-compatibility-probe.
- The same 9-line paths-ignore block is copy-pasted into 7 workflows, and it excludes DESCRIPTION, NAMESPACE, and .github/** everywhere.
- Branch filters are inconsistent: main; main+dev; main+dev+dev-*; main+integration; integration only. commit-lint covers main only, while most work lands on integration.
- Coverage is computed in three places with conflicting rules. test-coverage uploads to Codecov via OIDC and fails CI on upload error. pipeline-tests enforces a blocking 75% gate and uploads via token with no report file. coverage-check applies a warn-only 75% with the R/data.R exclusion.
- Dependency installation varies: setup-r-dependencies with differing extra-packages lists in most files, but raw install.packages plus actions/cache in test-quick.
- The db-* workflows are three near-identical copies. db-ecotox-source-only has ref: main and build-outcome handling that the other two lack.
- publish-rolling moves the tag before upload, while publish-integration moves it after all uploads. Shell style differs as well (`${{ github.repository }}` versus $GITHUB_REPOSITORY).
- The bot-actor skip `if: github.actor != 'github-actions[bot]'` is applied to r-cmd-check, test-coverage, coverage-check, cran-readiness, test-quick, and gitleaks, but not pipeline-tests or pkgdown.
- README drift: it references `R-CMD-check.yml` (actual file is r-cmd-check.yaml), says schema-check installs `wrapmaint` (the workflow runs dev/install_toolkit.R, which is apipak per cran-readiness), references the old db-ecotox.yml, omits db-dsstox, db-toxval, gitleaks, commit-lint, pipeline-tests, test-quick, and rebase-WIP, and says CI must not re-record cassettes while pipeline-tests has a rerecord input.

### amos-harmonizer, bsicons, sk_app, epa-sswqs (small repos: plain R-CMD-check, Shiny deploy, data-build)

## Keep-local decisions

These workflows and files stay in their own repositories and are not promoted to baseline. Project-specific workflows may still use the baseline composite actions (`r-setup`, `pkg-metadata`).

- ComptoxR cran-readiness.yml: apipak generation lane. Keep it local. Reuse only its toolkit_ref 40-hex SHA validation pattern and add permissions and concurrency.
- ComptoxR schema-check.yml: scheduled codegen PR against integration. Keep it local. Fix the env-passed PR body, raise the timeout to 30-45, and add concurrency.
- ComptoxR api-compatibility-probe.yml and record-cassettes.yml: live-API lanes. These are the only places CTX_API_KEY belongs. In record-cassettes, move inputs to env and integer-validate them, and add retention-days.
- ComptoxR pipeline-tests.yml: keep only the generator/pipeline tests. Delete the rerecord_cassettes input, the coverage gate, the no-op Codecov upload, and the dead issue step that uses dacbd/create-issue-action@main.
- ComptoxR db-dsstox.yml, db-toxval.yml, db-ecotox-source-only.yml: consolidate into one repo-local reusable db-build workflow based on db-ecotox-source-only (ref: main), with 3 thin cron callers and a shared concurrency group or pre-created db-latest to avoid the release-create race.
- ComptoxR test-quick.yml and coverage-check.yml: delete. They are redundant with r-cmd-check, test-coverage, and codecov.yml.
- ComptoxR rebase-WIP-branches.yml: delete. It has an expression typo `github.event. review.state` (line 11), hyphen prefixes that do not match Conventional Branch names, and automatic force-pushes of other branches.
- concert track-comptoxr-release.yaml: keep it local. Copy it to chorus to replace ComptoxR@*release. Promote it to a baseline 'track-remote-pin' workflow only after both repos run it. Pin checkout by SHA, add concurrency, and fix the bot email to 41898282+.
- concert r-cmd-check locked-review test filter 'review|modules-render': this stays in concert's caller as an input to r-renv-tests.
- maestro build.yml (Tauri: Node + Rust): keep it project-specific. Fix rust-cache to workspaces '. -> target', use npm ci with cache: npm, move to Node 22/24, add a fast lint/typecheck/clippy job that the build job needs, and add permissions, concurrency, and timeout. Add only the gitleaks and commit-lint callers from baseline. Do not add Node or Rust composites to baseline for one consumer.
- epa-sswqs build-toxval.yml: a targets-to-dated-release data build. Keep it local. Scope secrets to steps, add timeout, concurrency, a file-existence check, and create-before-delete release ordering, and use r-version: renv. A generic data-release template is not justified yet; revisit if a second data-build repo appears.
- bsicons R-CMD-check.yaml: this is upstream rstudio boilerplate on a fork. Do not migrate it. Disable Actions on the fork or delete the file, because its website and routine jobs can deploy or push to the fork.
- ComptoxR check_public_api, the stable-profile build, and the TESTTHAT_PARALLEL (#253) workaround: pass these as caller inputs. Do not hardcode them in templates.
- serapeum ISSUE_TEMPLATE and PULL_REQUEST_TEMPLATE: project-specific. Genericize them into a separate public seanthimons/.github community-health repo if wanted, not into baseline.
